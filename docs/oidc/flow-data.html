OIDC 로그인 흐름: 실제 주고받는 데이터

누가 누구에게 어떤 모양으로 보내는지 1번부터 10번까지 따라갑니다. 값은 shop RP와 이 레포의 IdP를 기준으로 한 예시입니다.

먼저, Referer가 뭐야?

브라우저가 "나 이 페이지에서 왔어"라고 다음 서버에 알려 주는 요청 헤더입니다. 철자는 원래 표준에 오타가 난 그대로 굳어서 r이 하나입니다.

사용자가 blog.com 글에서 shop.com 링크를 클릭하면

GET / HTTP/1.1
Host: shop.com
Referer: https://blog.com/post/1     ← 브라우저가 자동으로 붙임

code와 무슨 상관? 7번이 끝나면 브라우저는 /callback?code=Xy7... 주소에 있습니다. 이 페이지가 외부 이미지를 불러오거나 외부 링크로 나가면, 그 외부 서버에 주소가 전달될 수 있습니다.

GET /ad.png HTTP/1.1
Host: ads.example
Referer: http://localhost:4000/callback?code=Xy7...&state=st123     ← 위험한 경우

요즘 브라우저는 기본값(strict-origin-when-cross-origin)으로 다른 사이트에 http://localhost:4000/까지만 보냅니다. 그래서 위 경우는 사이트가 정책을 느슨하게 풀었거나 오래된 브라우저일 때 생깁니다. 제가 앞에서 "Referer에 남을 수 있다"고 한 건 기본 동작이 아니라 이런 예외입니다. code가 URL에 실리는 이상 방문 기록, 서버 로그 같은 다른 노출 경로도 있어서 만료를 짧게 둡니다.

전체 흐름

주소가 보임 브라우저를 거침 (주소창·방문 기록·로그) 서버끼리 브라우저를 거치지 않음 내부 처리 네트워크로 안 나감

8~10번은 단계 5 이후에 만들 부분이라, SPEC 기준의 예정 모양입니다. RP(1~3, 7, 10번의 RP 쪽 처리)는 이 레포 범위 밖입니다.

값 따라가기:
RP 서버shop · :4000
브라우저사용자
IdP우리 서버 · :3011
로그인 클릭
1 브라우저 → RP
GET /login HTTP/1.1
Host: localhost:4000
값 만들기
2 RP 안에서 내부 처리
state         = st123
nonce         = n456
code_verifier = dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk   ← 비밀, 아직 아무에게도 안 보냄
code_challenge = S256(code_verifier)
              = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
302 + 쿠키
3 RP → 브라우저 주소가 보임
HTTP/1.1 302 Found
Set-Cookie: state=st123; nonce=n456; verifier=dBjf...   (예시, HttpOnly 쿠키)
Location: http://localhost:3011/api/oidc/authorize?...   (4번 주소)
GET /authorize
4 브라우저 → IdP 주소가 보임
GET /api/oidc/authorize
  ?response_type=code
  &client_id=shop
  &redirect_uri=http://localhost:4000/callback
  &scope=openid profile email
  &state=st123
  &nonce=n456
  &code_challenge=E9Melhoa...     ← 해시만 나감. verifier는 안 나감
  &code_challenge_method=S256
code 발급·저장
5~6 IdP 안에서 내부 처리

RP·파라미터·로그인을 확인한 뒤 code 원문을 만들고, DB에는 해시로 저장합니다.

oidc_authorization_code 테이블의 한 행
{
  code_hash:      "sha256(Xy7...)",    ← 원문 아님
  client_id:      "shop",
  user_id:        "dev-user",
  redirect_uri:   "http://localhost:4000/callback",
  scope:          "openid profile email",
  nonce:          "n456",
  code_challenge: "E9Melhoa...",
  auth_time:      "12:40:00",
  expires_at:     "12:45:00",           ← 5분 뒤
  used_at:        null
}

state는 저장하지 않습니다. 받은 값을 7번 주소에 그대로 돌려주기만 합니다.

302 → /callback (브라우저가 이어서 전달)
7 IdP → 브라우저 → RP 주소가 보임
IdP의 응답
HTTP/1.1 302 Found
Location: http://localhost:4000/callback?code=Xy7...&state=st123

브라우저가 이어서 보내는 요청
GET /callback?code=Xy7...&state=st123 HTTP/1.1
Host: localhost:4000
Cookie: state=st123; nonce=n456; verifier=dBjf...

code 원문이 URL에 실리는 구간입니다. RP는 주소의 state와 쿠키의 state가 같은지 비교합니다.

POST /token
8 RP → IdP 서버끼리
POST /api/oidc/token HTTP/1.1
Authorization: Basic base64(shop:client_secret)      ← "나는 shop이다"
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code
&code=Xy7...
&redirect_uri=http://localhost:4000/callback
&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk      ← 비밀이 처음 밖으로 나감

여기에 nonce와 state는 없습니다. IdP의 확인 순서: 해시로 code 행 찾기 → 만료·1회용 확인 → 같은 client인지, 같은 redirect_uri인지 확인 → S256(verifier) === 저장된 code_challenge

토큰 응답 (JSON)
9 IdP → RP 서버끼리
HTTP/1.1 200 OK
Content-Type: application/json

{
  "id_token":     "eyJhbGci...헤더.페이로드.서명",   ← 신분증
  "access_token": "...",                            ← 출입증
  "token_type":   "Bearer",
  "expires_in":   3600
}

id_token의 페이로드를 풀어 보면
{
  "iss":   "http://localhost:3011/api/oidc",
  "aud":   "shop",
  "sub":   "dev-user",
  "nonce": "n456",                  ← 5~6번에서 저장한 값을 그대로 넣음
  "iat":   1793420400,
  "exp":   1793424000
}
검증 후 로그인
10 RP 안에서 내부 처리
1. /jwks의 공개키로 id_token 서명 확인
2. iss, aud, exp 확인
3. id_token의 nonce === 쿠키의 nonce
4. sub로 RP 자체 세션 생성 → 로그인 완료

아까 헷갈린 3가지

1. nonce는 왜 code와 같이 저장할까?

2번RP가 만듦
4번IdP가 받음
5~6번code 행에 저장
8번안 옴
9번id_token에 넣음
10번RP가 비교

8번에 nonce가 안 오기 때문에, 저장해 두지 않으면 9번에서 넣을 값이 없습니다.

2. code_challenge는 뭘 증명할까?

값증명하는 것수명
client_secret"나는 shop이다" (RP 신원)RP당 고정
code_verifier"이번 로그인을 시작한 게 나다"로그인 1번마다 새로

code만 훔친 사람의 8번 요청은 이렇게 끝납니다.

POST /token  code=Xy7...  (code_verifier 없음, 또는 틀린 값)
→ S256(verifier) ≠ 저장된 code_challenge
→ 400 {"error":"invalid_grant"}

3. code 만료는 왜 짧게 할까?

5~6번IdP가 발급, DB엔 해시
7번URL에 원문 노출
IdP → 브라우저 → RP
8번IdP로 돌아감
서버끼리

"URL에 담겨 IdP로 온다"가 아니라, URL에 실리는 건 IdP에서 RP로 가는 7번이고, IdP로 돌아오는 8번은 URL에 보이지 않습니다. 7번에서 샜을 때 쓸 수 있는 시간을 줄이려고 만료를 짧게 둡니다.
